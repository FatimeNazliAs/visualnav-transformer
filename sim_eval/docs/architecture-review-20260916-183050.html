Architecture Review

sim_eval/ — after P1

P1 closed the loop: NoMaD's brain now drives the simulator's body. 1,920 lines across 12 modules, 37 GPU-free tests, one working rollout. This review asks a narrower question than "is it good" — where will P2, P3 and P4 have to change this code rather than add to it? That is the signal of a missing seam.

The pattern behind every candidate

P1's three brain-side seams are clean and deep: nomad_policy (the network), pd_control (the steering), checkpoints (which arm, at what resolution). Each hides a lot behind a small interface, and each is tested through that interface.

The friction is all on the harness side. Two of the five components the plan names — the topomap builder and the scorer/recorder — have no module, so their responsibilities are currently spread thin across bridge.py and the two entry-point scripts. That is fine for P1, which only had to prove one rollout works. It stops being fine at P2, which rewrites the trail producer, and at P3, which owns episode rules.

Candidates

Eight. G comes first because it is the only one that can make the final numbers wrong rather than merely make the next phase awkward.

Candidate G · top recommendation

The localization window is a proven bug site with zero tests

Strong

Files

nomad_policy.py:173–188 the window math
nomad_policy.py:139 load_model inside __init__
232 lines, 0 tests — the largest untested block in the package

Problem

Five lines decide which topomap node the robot steers toward:

start = max(closest_node - radius, 0)
end   = min(closest_node + radius + 1, goal_node)
min_idx      = argmin(dists)
closest_node = min_idx + start
sg_idx = min(min_idx + (dists[min_idx] < thresh), len-1)

Pure index arithmetic over a numpy array, and upstream has already shipped this bug once: commit 7b5b24c "Fix closest node update for topomap localization" replaced closest_node = np.argmin(distances) with start + min_dist_idx — a window-relative index used as an absolute one. My port has it right. Nothing proves it stays right.

The failure mode is the nasty one: an off-by-one here produces a robot that drives plausibly, toward the wrong node. You cannot see it in a GIF, and it would silently corrupt every number in P6's table.

Why it isn't tested

NomadPolicy.__init__:139 calls load_model → torch.load → .to(device). The object cannot exist without real weights and a GPU. To reach five lines of arithmetic you would have to stub the whole model protocol — a string-dispatching callable answering three different call shapes, plus DDPMScheduler and get_action.

Solution — cheaper than injection

Don't build a model-injection seam. Just name the arithmetic: lift those lines into a pure localize(dists, closest_node, radius, goal_node, close_threshold) → (start, closest_node, sg_idx), called by act(). The numbers are unchanged, so fidelity to navigate.py is preserved and still diff-able — but it becomes testable with a hand-written list of distances, no torch, no GPU, no weights.

Benefits

  • The asymmetry is the argument: the other verbatim port, pd_control.py, has 10 tests and is the best-pinned module here. The policy port — longer, and the one with a real bug in its history — has none.
  • Leverage: the deletion test inverts here. Extracting concentrates the risky logic into a named, tested unit, and leaves act() as plumbing.
  • Tests: window clamping at both ends, the start offset, and the close-threshold step become ~8 assertions costing nothing to run.

Candidate A

The trail is a concept with no module

Strong

Files

p1_0_make_topomap.py:101,144–148 (writes)
bridge.py:57 load_topomap (reads the images)
p1_1_drive_test.py:63–75,137–139 (reads the poses)

Problem

A trail is one thing: numbered node images, the pose each was taken from, and the start pose. Right now its format is invented in one file, its images are loaded in a second, and its poses are dug out of a raw dict in a third — route["nodes"][-1]["pose"] at p1_1_drive_test.py:139. Nothing owns the contract, so nothing can validate it and nothing can be tested against it.

Solution

A trail.py module that reads and writes its own format: Trail.save(dir), Trail.load(dir), with .nodes (image + pose), .start_pose, .goal_pose, .reference_path_length. load_topomap moves out of bridge.py; read_start_pose disappears from the script.

Benefits

  • Locality: one file answers "what is a trail and what can I ask it". Today that needs three.
  • Leverage: P2 replaces only the producer (scripted route → the sim's own planner) and inherits the reader unchanged. P3 gets reference_path_length — which it needs for the timeout and for SPL's denominator — from the module that already knows the node poses.
  • Tests: round-tripping a fabricated trail through save/load needs no GPU and no iGibson, so the format becomes the test surface. Today it is untestable without driving the simulator.

Candidate B

Episode rules are scattered across four places

Strong

Files

bridge.py:234 reached_goal · bridge.py:273–292 run
bridge.py:137,146,165 collision_ticks on SimBody
p1_1_drive_test.py:35 DEFAULT_MAX_TICKS · :96–120 report

Problem

"When does an episode end, and how did it go" is currently four fragments: the stopping rule lives on NomadBridge, the tick budget is a constant in a script, the collision count is a mutable counter on SimBody (the body has no business scoring), and the outcome is computed inside the script's report() — as print statements, not a value. Plan §6 defines five metrics and two termination conditions; P3 cannot add any of them without editing run().

Three sharper points found on a second pass:

· reached_goal (bridge.py:234) is topomap localization, not geometry — plan §5 defines success as within ≈1 m of the goal pose, and the bridge holds no goal pose at all (start_episode takes only a start pose). This property must change, not extend.

· collision_ticks counts ticks with any contact, not collision events, and has no per-metre normalisation — plan §6 asks for "collisions per episode / per meter". It is also reset by SimBody.reset, so the body controls when the score resets.

· report() at p1_1:100–107 already computes two of §6's five metrics (final distance-to-goal, path length) — inside a print function, in a phase-numbered script. P3 must lift or duplicate them.

Solution

An episode.py owning termination and outcome. NomadBridge narrows to one job — produce the next TickRecord — and the episode decides whether to ask for another. Success radius, timeout-from-reference-length, collision tally and distance-to-goal become fields on an EpisodeOutcome that P3 writes to CSV and P1's script prints.

Benefits

  • Leverage: P3 becomes additive. Today it is a rewrite of the loop that P1 just validated — the riskiest possible change.
  • Locality: §6's rules read as one file instead of being inferred from a loop, a constant and a print block.
  • Tests: termination is pure logic over poses and counters. Fed a fake tick stream it tests with no GPU, no iGibson and no model — which is exactly the logic that decides every number in the final table, and is 0% covered today.

Candidate C

run() holds every frame of the episode in memory

Strong

Files

bridge.py:273–292 run() → list[TickRecord]
bridge.py:206 TickRecord.frame — a full PIL image
p1_1_drive_test.py:84–94 write_frames, after the run finishes

Problem

run() returns a list, and every element pins a decoded 640×480 frame. Measured: 0.92 MB per frame in RAM, so P1's 39-tick run held 36 MB and a 200-tick episode would hold 184 MB before a single byte is written. Worse, the frames are only written after the loop — so a crash or a timeout at tick 199 loses the whole recording, which is the one artefact you wanted from a failed episode. On disk P1 measured 0.51 MB/frame; P6's 40 rollouts at 200 ticks project to ~4 GB of PNGs.

Two real bugs in the writer, found on a second pass:

· write_frames raises IndexError at p1_1:92 (frames[0]) on an empty record list — reachable with --max-ticks 0, or any run that stops before its first tick.

· It deletes every *.png in the output directory (p1_1:84–85) before writing. Harmless for one flat run; actively destructive once P4 puts per-episode subdirectories under there.

Solution

Invert it. The on_tick callback already exists at bridge.py:280 — promote it from a progress hook to the interface, make the tick loop a generator, and stop returning the list. A consumer that wants the frames (P4's recorder) encodes each one as it arrives; a consumer that only wants numbers (P3's scorer) never holds a frame at all.

Benefits

  • Leverage: P4's recorder becomes a sink you plug in, not a post-processing pass over an accumulated list. P6's memory stops scaling with episode length.
  • Locality: "what happens to a frame" is answered in one place instead of being split between the loop that keeps it and the function that writes it 90 lines later.
  • Tests: a sink is trivially fakeable — collect into a list in a test and assert on it — so the loop's behaviour becomes testable without writing 20 MB to disk.

Before / after — memory over an episode

Measured, not estimated: 640×480×3 bytes per decoded frame, and 20.5 MB on disk for P1's 39 frames. The flat line is the same loop with the frame handed to a sink instead of retained.

Candidate D

SimBody's seam already leaks — callers reach through .env

Worth exploring

Files

bridge.py:112–190 SimBody
p1_0_make_topomap.py:121 body.env.simulator.renderer · :126–127 body.env.task.initial_pos/orn
p1_1_drive_test.py:149 body.env.simulator.renderer

Problem

This is not a prediction — it is already happening. SimBody is meant to be the adapter over iGibson, but three call sites in two scripts reach past it into .env.simulator.renderer and .env.task. The interface does not cover what its callers need, so they bypass it. The reason is a conflation: SimBody mixes robot questions (observe, command, pose) with world questions (which GPU is rendering, where may the robot start). Plan §6 and §4 pile more world questions on: P3 needs geodesic distance and start/goal sampling for SPL, P4 needs the traversability map for the top-down view. All of those would leak the same way.

Solution

Split along the conflation: SimBody keeps observe / command / pose / place; a SimScene answers world questions — sample_pose, geodesic_distance, trav_map, verify_gpu — and .env stops being public. Lighter alternative: keep one class and just widen it until nothing reaches through.

Benefits

  • Leverage: the iGibson version and its API quirks stay behind one seam. That matters here — P1 already found one (the LoCoBot's inverted angular velocity, bridge.py:117–130); the next will want the same single home.
  • Locality: "everything we ask the simulator" in two files instead of two files plus three reach-throughs.
  • Tests: a named world interface can be faked. Today nothing that touches SimBody is testable at all — 0 of the 37 tests cover it, because faking it means faking env.simulator.renderer and env.task too.

Candidate E

Two scene configs share 38 of 51 substantive lines

Worth exploring

Files

configs/locobot_rs_static.yaml (92 lines, 51 substantive)
configs/locobot_rs_bridge.yaml (111 lines, 51 substantive)
measured: 13 substantive lines differ

Problem

The bridge config is the smoke-test config with six settings changed. The other 38 lines — camera, traversability, rewards, sensors — are duplicated, and they are exactly the settings that define what world is being rendered. If vertical_fov or image_width is tuned in one (and P5 is explicitly expected to revisit FoV), P0's smoke test quietly starts describing a different world than the bridge drives. Plan §B scales to 2 then 3 houses, so scene_id must vary — today that means more whole-file copies.

Solution

One base config plus small named overlays, merged in Python. Verified feasible: iGibson's parse_config accepts a Mapping as well as a path (igibson/utils/utils.py:29), so iGibsonEnv(config_file=<dict>) works — no temp files needed. Each overlay then documents itself: the bridge overlay is six lines that are exactly the six deliberate differences.

Benefits

  • Leverage: a new house is one line, not a 92-line copy. Plan §7's identical-world requirement becomes structural rather than a promise.
  • Locality: the diff between P0's world and P1's world is readable in one place — currently you must diff two files to find it.
  • Tests: the merge is pure dict logic; a test can assert the overlay changes exactly the intended keys and nothing else.

Candidate F

The config validator and its consumer disagree about what's required

Worth exploring

Files

checkpoints.py:27–37 REQUIRED_PARAMS · :104–117 validate_params
nomad_policy.py:66–98 build_model — the actual consumer

Problem

checkpoints.py promises to fail loudly rather than guess — that is its whole reason to exist, because a wrong image_size would silently invalidate the fairness protocol. But its REQUIRED_PARAMS list omits five keys that build_model actually reads: mha_num_attention_heads, mha_num_attention_layers, mha_ff_dim_factor, down_dims, cond_predict_scale. A log missing any of them passes validation and then dies with a bare KeyError deep inside model construction — the exact failure mode the module was written to prevent. The two lists are in different files and nothing keeps them honest.

Solution

Let the consumer declare its own needs — the model builder exports the keys it reads, and checkpoints validates against that rather than against a hand-maintained copy. Cheapest version: one test that asserts every key build_model reads appears in REQUIRED_PARAMS.

Benefits

  • Leverage: small, but it protects the module the whole fairness protocol rests on. P7 adds the ctx3/stride3/160×120 arms — more logs, more chances for one to be incomplete.
  • Locality: "what a checkpoint config must contain" answered once, next to the code that consumes it.
  • Tests: becomes a single assertion that cannot drift, versus today's list which is already wrong.

Candidate H

The package has no packaging — six small duplications, and tests that can't run where they claim

Worth exploring

Problem

Individually trivial, collectively a pattern: sim_eval/ has no __init__.py, no conftest.py and no test runner, so every module and every test re-derives its own environment. Each item below is verified.

  • · save_rgb (p0_1:80–86) and frame_to_pil (bridge.py:46–54) are the same float→uint8→PIL conversion, twice.
  • · The arg re-quoting loop in run_p0_smoke_test.sh:22–25 and run_p1_drive_test.sh:33–36 is byte-identical, comment included (diffed: no output). Same for the chown line. lib.sh is the obvious home and has neither.
  • · SIM_EVAL_DIR = Path(__file__)… appears in 5 modules.
  • · sys.path.insert(0, parents[1]) appears in all 4 test files — what a conftest.py exists to remove.
  • · Stale-PNG clearing is written twice (p1_0:68–76, p1_1:83–85).
  • · Every other entry point has a run_*.sh; the tests do not, so the one thing you run most often is the one thing with no wrapper.

And the docstrings overclaim

Three test files say "Runs anywhere: no GPU, no iGibson, no container." Verified false: the host has no python on PATH (only python3) and no pytest. Worse, bridge.py:33 imports pybullet at module scope while importing iGibson lazily — so test_context_queue.py needs the container, directly contradicting its own docstring. A comment that claims a property nothing enforces is worse than no comment: it is the kind of thing a future reader trusts.

Solution

A conftest.py (kills 4 copies), a paths.py or package __init__ (kills 5), sim_exec gaining the arg-quoting and chown (kills 2 shell copies), frame_to_pil used by P0 (kills 1), a run_tests.sh, and pybullet moved into the function that uses it — which makes the docstrings true instead of aspirational.

Applied the deletion test, left them alone

Four things looked shallow and are not. Recording them so a later review doesn't re-litigate.

ContextQueue bridge.py:74–110

37 lines behind a 4-method interface — suspiciously thin. But inlining it into NomadBridge would put an off-by-one that silently feeds the encoder the wrong frame count back into the tick loop, where it is untestable. Complexity would spread. Keep.

TickRecord bridge.py:196–220 — revised

I first passed this as a fine value object. On a second look it is the clearest shallow class here: 9 positional params → 9 identical attributes, and it is an exhaustive copy that already drops the two fields P4 needs — PolicyStep.distances and .samples are set at nomad_policy.py:195–196 and never read anywhere in the repo (verified by grep). So every future phase pays a 3-site edit: constructor, construction site, consumers. Fold into candidate B rather than keeping as-is.

pd_control.py 92 lines

Two functions and a small value class. Deleting it concentrates nothing — it would just move the verbatim port into bridge.py and cost the 10 tests that pin decision E. It is the best-tested module in the package. Keep, untouched.

the training-log parse checkpoints.py:78–101

Parsing a repr'd dict out of a 590 KB log looks like a hack worth removing. It is not: it is the only surviving record of what each arm was trained with, and it is correctly isolated behind one small interface. Keep the seam; candidate F only tightens what it checks.

Deliberately not proposed

Nothing here touches the ported control logic. The diffusion loop (nomad_policy.py:198–232), the localization window (:170–186), the PD mapping (pd_control.py:70–92) and the retained no-op split/cat at nomad_policy.py:152–155 are all verbatim from deployment/src/ by requirement (plan decision E, CLAUDE.md "reuse by copy"). Fidelity beats elegance there, and the fact that it looks improvable is the point — a future reader must be able to diff it against the deployment stack. Likewise SimBody.ANGULAR_VELOCITY_SIGN is not a magic constant to clean up; it is a measured correction for an iGibson bug.

Outside the code: this workstream has no conventions file of its own

The auto-loaded CLAUDE.md documents a different workstream — deeper_visuals/, container naz_nomad_deeper_viz, the visualization plan. It never mentions sim_eval. So sim_eval's real conventions live only in plan §3b/§3c, and the two sources already conflict where they overlap: CLAUDE.md makes this architecture pass mandatory at the end of every phase, while plan §3b makes it explicitly optional. The "reuse by copy, not import" rule is scoped to debug_visuals/ there, yet sim_eval is the code actually relying on it.

There is also no CONTEXT.md and no docs/adr/, which is why this review had to take its domain vocabulary from a plan file. Worth fixing before P3 multiplies the number of terms (episode, rollout, arm, trail, scorer) that currently have no written definition. Not a code candidate — flagging it because it is friction a future reader (human or model) will hit first.

Top recommendation

Candidate G — name and pin the localization math. Then A.

Because it is the only candidate that can make the final numbers wrong. Everything else on this page makes a future phase awkward. G is five lines of index arithmetic that decide which node the robot steers toward, in a 232-line module with zero tests, and upstream has already shipped this exact bug once (7b5b24c). The failure mode is a robot that drives plausibly toward the wrong node — invisible in a GIF, fatal to a ranking of arms. The whole justification for building this harness is that the open-loop "best" rested on a proxy; a silent off-by-one here would replace one untrustworthy ruler with another.

It is also cheaper than it looks. Don't build a model-injection seam — just lift the arithmetic into a pure localize() and test it with a hand-written list of distances. The numbers don't change, so fidelity to navigate.py survives, and the module that is currently the least-tested port gets the same treatment as pd_control.py, which is the best-tested thing here. Cost: an hour. Blast radius: one function. Do it before committing P1.

Then A, before P2 starts — P2 is the trail builder, and if the seam goes in first P2 adds a producer behind an existing interface instead of rewriting three files while P1's only validated rollout is unreproducible.

B and C together, at the start of P3. Both reshape run(), so doing them separately means touching it twice; B also absorbs the TickRecord revision. That is what makes P3 additive rather than a rewrite of the loop P1 just proved.

D, E, F, H are real and none is urgent. F and the write_frames crash are ~20-minute fixes that can ride along with anything. E pays off the moment P2 adds a second house. H is worth one cleanup sitting, mostly so the test docstrings stop claiming something untrue. D deserves a revisit once P3 exists and its second consumer makes the seam fully real.
