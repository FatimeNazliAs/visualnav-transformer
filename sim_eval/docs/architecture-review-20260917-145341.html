Architecture review · deepening opportunities

sim_eval — after P4 (the recorder)

The closed-loop evaluation harness: NoMaD's brain driving an iGibson body, scored against a fixed task set, and — since P4 — filmed while it is scored. This review does not ask "is this code good". It asks the narrower, more useful question the P1 review asked:

Where will P5 and P6 have to change this code rather than add to it?

A phase that must rewrite existing code is the signal of a missing or misplaced seam. That framing is what orders the candidates below.

Vocabulary. There is still no CONTEXT.md and no docs/adr/ in this repo, so — as in the P1 review — the domain terms come from the plan and the README (trail · node · subgoal · control tick · episode · arm · scorer · recorder) and the architecture terms from the skill (module · interface · depth · shallow · seam · adapter · locality · leverage · the deletion test). Candidates the P1 review settled are not re-litigated; two of its open ones are carried forward with new evidence.

The pattern behind this round

P4 went in cleanly: the recorder is a deep module — 597 lines behind capture(record) — and it did not touch episode_runner.py at all, because P3.5 had already opened the right seam (the episode is a stream, the consumer holds the tick loop). That is the system working.

But P4 also did something worth noticing: to draw the top-down panel it had to reach runner.body.env.scene — through the adapter, into the simulator. That is not a new idea. The P1 review predicted it in writing:

"P3 needs geodesic distance and start/goal sampling for SPL; P4 needs the traversability map. All would leak the same way." — architecture-review-20260916.md, candidate D, marked Open

Both predictions came true, exactly. The leak count has gone from ~5 to 12. Every finding below is either that seam, or the same shape of problem: a knob, a runner or a config that has no module of its own, so each phase copies it again.

Candidates

Six, ordered by how soon P5 or P6 collides with them.

A — The simulator adapter leaks, and P4 widened the hole

Strong

Files

bridge.py:132–209 SimBody · and the twelve call sites that reach past it:
episode_runner.py:284 body.env.scene.floor_heights · episode_runner.py:385 body.env.scene (new in P3)
run_eval.py:181 runner.body.env.scene (new in P4) · topomap_builder.py:249,496 · p1_0_make_topomap.py:121,126,127 · p1_1_drive_test.py:184 · p2_1_build_test.py:210,219 · run_eval.py:207

Problem

SimBody is meant to be the adapter over iGibson. Its interface covers the robot — observe · command · pose · place · reset · close — and nothing else. But callers need world answers too: which GPU is rendering, the floor's height, the geodesic distance to a goal, the traversability map. None of those are on the interface, so twelve call sites reach through .env into the thing being adapted. An adapter whose callers bypass it is not protecting anything.

Two aggravations, both measured:

  • gpu.verify_renderer(body.env.simulator.renderer, selected_gpu) appears verbatim at 5 call sites, each reaching three levels deep — and getting it wrong means silently rendering on a teammate's GPU, which is the one mistake this workstream's plan §3c says must never happen.
  • SimBody.ANGULAR_VELOCITY_SIGN — the line the README itself names as the most breakable in the package — still has zero tests, because SimBody cannot be constructed without a GPU. The 176 tests cover everything around it.
Before — one narrow adapter, pierced 12×
After — split along the conflation

Solution

Split along the conflation the P1 review named. SimBody keeps the robot; a new SimScene module answers world questions — floor height, geodesic distance, the traversability map, and "is the renderer on the GPU I pinned" — and .env stops being public. The lighter variant is to keep one class and widen it until nothing reaches through; the split is preferable because the two halves have different lifetimes (one body per scene, many episodes).

Deletion test: inlining SimBody into its callers would scatter iGibson trivia across seven files — complexity spreads, so it is deep and stays. This is not a shallow module to delete; it is a deep module with too narrow an interface, and the fix is to widen the seam rather than remove it.

Benefits

Locality
"How does this harness talk to iGibson" becomes two files to read instead of seven.
Leverage
P5/P6 add scenes and a second house behind an interface that already covers what they ask.
The test surface
A fake SimScene makes ANGULAR_VELOCITY_SIGN and the floor-height lookup testable without a GPU — today they are untestable by construction.

B — The four knobs P5 is about to turn have no config and no provenance

Strong

Files

nomad_policy.py:31–34 the four module constants · nomad_policy.py:174–176 the constructor that defaults to them · run_eval.py:255 and p1_1_drive_test.py:181 — both call NomadPolicy(spec, device) with no knobs · configs/eval.yaml (no policy section) · metrics.py:38–65 (no policy column)

Problem

Four numbers decide how the model steers: num_samples=8, waypoint=2, radius=4, close_threshold=3. They are navigate.py's argparse defaults, ported faithfully — and they are reachable only by editing the module. Every other dial in this harness has a config section and a column in the metrics table; these have neither.

P5's whole job, in the plan, is "confirm NoMaD behaves sanely despite the domain gap; sanity-tune only what fidelity allows." So P5 will turn these knobs, repeatedly. Today each turn is a source edit, and — worse — two CSVs produced from two different tunings are byte-identical in their provenance columns. The fairness protocol (plan §7) says "mirror the real robot config for all arms; no per-arm tuning"; right now that is an assertion in a document rather than something the table can prove.

The only four dials with no config and no record are the four P5 exists to turn.

After — a driver section, and a column
# configs/eval.yaml
driver:              # navigate.py's own defaults
  num_samples: 8     # -n
  waypoint: 2        # -w
  radius: 4          # -r
  close_threshold: 3 # -t
# every row of the table
checkpoint,task_id,seed,...,
driver   # "n8 w2 r4 t3"

One column. A P5 tuning sweep becomes a set of comparable tables instead of a set of indistinguishable ones, and P6's fairness claim becomes checkable rather than asserted.

Reads against plan decision E ("mirror the real LoCoBot exactly; tune nothing") — but does not violate it. Nothing here changes a default. It makes the existing defaults explicit and records which ones ran. Decision E is precisely the invariant a recorded column proves. If you would rather forbid the section outright, that is a decision worth writing down as the repo's first ADR so a later review does not propose it again.

Benefits

Locality
What the driver was set to lives beside what the task was — in one YAML, in one row.
Leverage
P5 sweeps by editing config; no source edit, no rebuild, no ambiguity about what produced which table.
The test surface
A DriverConfig is testable exactly like EpisodeRules and RecordingConfig already are — no GPU, no checkpoint.

Solution

Deletion test: inlining run_scene into score_checkpoint today would concentrate — which is the tell that it is shallow. That argues either for folding it in or for giving it a real object to hang on; the run object is the version that also pays off for P5 and P6.

D — Six shell runners are the same thirteen lines; P5 will make it seven

Worth exploring

Files

Problem

diff run_p3_score_test.sh run_p4_record_test.sh returns only the header comment and one line — the script name. The body is identical in all six: cd, source lib.sh, echo the GPU, re-quote "$@", sim_exec python -u <script>, chown the outputs back. lib.sh already centralises the shared settings; nothing centralises the shared body.

The drift has already started, harmlessly but visibly: the GPU prologue prints "GPU:    " in two scripts and "GPU:        " in five. That is what copy-paste looks like before it costs something.

E — The config that decides everything P6 runs has zero tests

Worth exploring

Files

run_eval.py:50–91 EvalConfig — 307-line module, 0 tests, no tests/test_run_eval.py

Problem

Every other config class in this package is pinned by tests — TaskSetConfig (17), TopomapConfig (23), EpisodeRules (32), RecordingConfig (14 as of P4). EvalConfig, which composes all four and decides which tasks exist, when an episode ends, what gets filmed and where it lands, has none. It is also the one every P6 command goes through.

Its behaviours are genuinely non-obvious and all currently unpinned: an unknown key under episode: must raise rather than be ignored (it does — by falling through to a TypeError); relative paths resolve against sim_eval/ and not the cwd; recording.directory gets a default that must survive an absent recording: block. All three are testable in milliseconds with a YAML string — no GPU, no simulator.

F — Two scene configs still share 38 substantive lines (carried forward)

Speculative

configs/locobot_rs_static.yaml and configs/locobot_rs_bridge.yaml — candidate E of the P1 review, still open, unchanged since. The P1 review already verified the fix is feasible (igibson/utils/utils.py:29 — parse_config accepts a Mapping, so overlays can be merged in Python with no temp files).

Why it is only Speculative now: P2 made each task write its own world.yaml beside its trail, so the world a run uses is already pinned per task and travels with it. The duplication's remaining cost is the day P6 adds the second house — one more whole-file copy — and the day P5 tunes the camera FoV in one file and not the other. Re-rank this to Worth exploring the moment either happens.

Deliberately not proposed

The ported control logic

The diffusion loop, the PD mapping, the retained no-op split/cat — verbatim from deployment/src/ by requirement. Fidelity beats elegance; the fact that it looks improvable is the point, because a reader must be able to diff it against the deployment stack.

A cross-arm comparison module

P6 needs one (two CSVs → one table), and it does not exist. That is an add, not a change, so it is not architectural friction — metrics.read_table and aggregate already expose the right seam for it.

The two-GPU launch

Already solved and documented in run_eval.sh's header: the same script twice, SIM_GPU=0 and SIM_GPU=1, both reading one immutable task set. Nothing to deepen.

Top recommendation

A — widen the simulator seam, before P5 leans on it

It is the only candidate with a prediction on the record that came true twice. The P1 review said P3 would reach for geodesic distance and P4 for the traversability map, and that both would leak the same way. Both did — episode_runner.py:284,385 and run_eval.py:181 — and the leak count roughly doubled to twelve.

P5 is "confirm NoMaD behaves sanely", which in practice means asking the scene a great many new questions: where did it get stuck, what was traversable there, how far was it really. Every one of those questions, asked today, adds a thirteenth and fourteenth reach-through. Widening the seam first is the difference between P5 adding and P5 spreading.

It also buys the only test this package still visibly lacks: with a fake SimScene, ANGULAR_VELOCITY_SIGN — the line the README calls the most breakable in the package — becomes testable without a GPU.
